最后一行是**源码推算**：当前模式每次 region 锁获取前屏蔽 SIGUSR1，释放后恢复，
因此约为 `2 × lock_acq`，前段约 17,559 次/秒；不是内核 syscall trace 实测。
不能在 Wine 中直接禁用此保护：线程若持锁时被 Wine 的 SIGUSR1 挂起，可能阻塞
整个共享区域及 wineserver。该开关只适用于不使用这类挂起处理器的消费者。

“每 Present”是同窗口所有游戏线程的计数除以请求数，不代表操作均发生在渲染线程
或处于某一帧的关键路径。Present 请求也不是物理显示完成帧。
此次降速后，futex 尝试/Present 仅增加约 1.2%，region 锁/Present 约增加 3.8%；
未发现与四倍以上降速相称的调用量暴增。单次操作及调度等待可能变长，仍需计时验证。

## 计数含义和缺口

- `wait_fast_ok` 只统计初始 `try_satisfy` 成功；零超时、alert 等返回路径不一定
  计入。因此不能把其补数称为真正阻塞比例。
- `wait_blocked` 是注册后准备进入休眠路径的次数，同一 wait 可重复进入；
  `futex_sleeps` 是 futex_wait 尝试，可因 EAGAIN 立即返回，不等于真正睡眠或上下文切换数。
- `lock_contended = 0` 只说明没有走到该重试计数点。普通 pthread_mutex_lock
  即使阻塞后首次调用返回，也不会增加它；**不能据此判断无锁争用**。
- `wake_walks` 不是精确 futex_wake 次数，一次 walk 可能唤醒多个等待者。
- 当前 `wake_lat_* = 0` 是未启用计时，不能解读为零延迟。开启 NTSYNC_DEBUG
  同时会启用 watchdog、timedlock 和 5 秒 wait 切片，不适合作为不改变行为的测量开关。
- 不包含所有同步：Wine RtlWaitOnAddress / alert 的直接 futex、wineserver IPC、
  FEX 内部锁以及图形驱动/呈现 fence 不都经过这组计数器。
- 读取前后整个 MHW 进程 stat 的 user/system ticks 分别增加 11785 / 968，system
  占已消耗 CPU 时间的 7.59%。该窗口比计数器窗口宽，且 system 含所有内核工作；
  它不是同步耗时占比，也不含线程睡眠/排队时间。

下一步应将独立、默认关闭的计时观测与 NTSYNC_DEBUG 行为开关分离，测量 region
锁等待/持有时长、futex 返回原因和唤醒到运行的延迟，再与线程调度及 Present 对齐。
系统小核集中运行的异常仍按 [场景性能调查](mhw-performance-20260927.md) 跟进，
本轮未证明其触发源，也没有因这些计数调整 spin、调度或温控策略。
