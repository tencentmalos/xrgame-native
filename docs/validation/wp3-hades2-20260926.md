## 失败链路与对照

1. 原启动器文件缺失。
2. 直接执行 Release/Ship EXE 后，Steam 初始化请求 `steamclient64.dll` 失败。
   替换 `steam_api64.dll` 无法解决启动早期请求；原 DLL 已恢复并核对 SHA。
3. 加入 GBE `steamclient64.dll` 后出现 `Application load error 3:0000065432`。
   ColdClientLoader 本身仍不能完成该游戏启动。
4. GBE 自带的 x64 extra DLL 配合 loader 后，游戏进入 `ForgeRenderer` 初始化，
   随后报告 `Renderer creation failed`。这条对照没有使用 Steamless。
5. Vulkan loader 日志明确指出 Turnip 缺少可见的 `vk_icdGetInstanceProcAddr`。
   Android HAL 导出表隐藏了该函数，虽然编译时已启用 X11 WSI，Wine 仍无法加载它。
6. 两次启动还遇到独立的 ntsync 共享锁残留：wineserver 阻塞于
   `ntsync_userspace.v9.shm` 内的 futex。所有 Wine 进程退出后，备份并隔离该文件，
   下一次启动恢复。此处是早期手动恢复记录；后续自动隔离修复及复测见文末。

### 首次黑屏定位（调试器完成后）

PID 9963 的 guest 寄存器与原始栈指针经同次构建的符号表关联：
主线程在 `NtWaitForAlertByThreadId` / `SleepConditionVariableCS`，渲染调度线程
在 `NtWaitForSingleObject`、DXGI Present 路径，`vkd3d-swapchain-sync` 在
`winevulkan!vkWaitForPresentKHR`。这是寄存器与栈中地址的符号关联，不能冒充完整 unwind。
该 Turnip 构建没有 `HAVE_X11_DRM`；普通 X11 硬件呈现路径不可用。
`MESA_VK_WSI_DEBUG=sw,noshm` 改走 GPU 渲染、CPU 读回、XPutImage 呈现；
`MESA_VK_WSI_PRESENT_MODE=immediate` 避开依赖 Present 事件的排队路径。
仅这两项仍黑屏。XPutImage 分支没有推进 `chain->present_id`，但驱动仍声明
present-wait；VKD3D 同步线程因此一直等 `vkWaitForPresentKHR`。
再设 `VKD3D_DISABLE_EXTENSIONS=VK_KHR_present_wait,VK_KHR_present_id` 后，
同一套 xrg3 二进制成功显示主菜单，并进入可响应键盘移动的实际游戏场景。

## AHardwareBuffer 呈现修复（20:19 起，xrg5）

固定 Turnip 的 Android/X11 WSI 使用 AHardwareBuffer 分配可供 GPU 采样和渲染的
swapchain image，以 DRI3 socket/修饰符 1255 交给 app。Guest 等待渲染 fence，
app 的 Vulkan renderer 导入共享图像并执行一次 GPU→GPU 拷贝，完成 fence 后发送
Present Complete/Idle，允许 guest 重用图像及推进 present ID。此路径没有 CPU
读回或纹理重新上传，但仍有 GPU 拷贝和同步成本，不能称为完全零拷贝。

- `xrg4` 首次复测缺少 `libxcb-dri3.so` / `libxcb-present.so`，Vulkan ICD 无法加载。
  临时补依赖后又暴露公共初始化清零 `image_type`，未创建 X11 pixmap，收到 BadPixmap。
  两次失败均保留在私有 `attempt19-ahb4.log` 和截图中。
- `xrg5` 修正图像类型初始化，并在驱动 ZIP 内携带源码构建的 XCB DRI3/Present
  库、MIT notice、源码归档 SHA。app 安装时校验并部署依赖；复测前移除了手工补入的
  两个库，确认新包自动恢复的文件 SHA 与包内一致。
- 默认 picoXr 固定 Vulkan display renderer / DRI3，AHB 不作 CPU lock；错误接收的
  AHB 返回 BadAlloc，GPU 拷贝保持实际缓冲区像素格式。已有帧率限制继续作用于 Idle
  回压，picoXr 不再丢弃被后续帧替代的 Idle 通知。
- `NTSYNC_SHM` 改为每次运行独立的 app 私有文件；只在 Wine 进程全部停止后删除
  旧会话文件。退出时停止 Wine，旧执行回调不能清除新进程 PID。guest debugger
  继承目标的 `NTSYNC_SHM`。这是重启隔离，未宣称修改了 ntsync 库内部的 robust mutex。
